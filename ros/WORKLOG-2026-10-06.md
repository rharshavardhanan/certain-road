## 3. Torch on the GPU

already a CUDA 13 build, so **no change to `pyproject.toml` or `uv.lock` was needed**.

  `uv venv --system-site-packages --python /usr/bin/python3 .venv`, then `uv sync`.
- Result: `torch 2.13.0+cu130`, `torchvision 0.28.0+cu130`, `ultralytics 8.4.115`,
  `opencv 5.0.0`, `numpy 2.5.1`. `torch.cuda.is_available()` is True and the device is `Orin`.

  - conv + batchnorm + SiLU, GPU against CPU: max absolute difference 6.6e-7

## 4. ROS 2 Jazzy install

Script: `~/install_ros_jazzy.sh` (outside the repo). It follows the official
ros2-apt-source method from docs.ros.org and:

1. adds an **8 GB swapfile** (`/swapfile`, plus a line in `/etc/fstab`), because the Orin
   Nano has 7.3 GB RAM and no swap, and VS Code + RViz + torch use most of it
2. installs the official `ros2-apt-source` package (version 1.3.0)
3. installs `ros-jazzy-desktop`, `ros-dev-tools`, `ros-jazzy-vision-msgs`,
   `ros-jazzy-cv-bridge`, `python3-opencv`
4. adds `source /opt/ros/jazzy/setup.bash` to `~/.bashrc`

**Problem hit and fixed.** The first run stopped silently after `apt update`. The docs read
the ros2-apt-source version from `api.github.com`, and this network's public IP is over
GitHub's unauthenticated API rate limit ("API rate limit exceeded"). The lookup returned
nothing and `set -e` ended the script with no message. The script now reads the version
from the `github.com/.../releases/latest` redirect, which is not the API, downloads with
`curl -f`, checks the file is a real `.deb`, and prints `!! stopped at line N` on any error.

Installed: `ros-jazzy-desktop 0.11.0`, `ros-dev-tools 1.0.3`, `ros-jazzy-vision-msgs 4.1.1`.
Verified with `ros2 run demo_nodes_cpp talker` / `demo_nodes_py listener` ("I heard: Hello
World").

**numpy 2 is fine.** ROS Jazzy's message libraries are built against Ubuntu's numpy 1.26,
and the project venv has numpy 2.5.1. Checked: messages with fixed-size float arrays
(`PoseWithCovariance`), `vision_msgs/Detection2DArray` and a 640x640 `Image` all serialize
and deserialize, and publishing works. No separate environment is needed.

## 5. What was built

The pasted plan said to wrap the existing simulator so the camera view it "already
renders" goes out as `sensor_msgs/Image`. **The 2D simulator renders no camera image:**
`sim/project.py` turns each pothole straight into a box. A renderer was added first.

### The ROS graph

```
sim_node ──/camera/image_raw──▶ perception_node ──/perception/detections──▶ planner_node
   ▲      ──/sim/ground_truth─▶                                                  │
   └──────────────────────────────────── /cmd_vel (Twist) ◀──── RosTransport ◀───┘
```

| Node | Does | In | Out |
|---|---|---|---|
| `sim_node` | Steps the bicycle model (`sim.model.step`) with the latest `/cmd_vel`; renders the camera frame; runs the 8 trial-matrix scenarios in turn | `/cmd_vel` | `/camera/image_raw`, `/sim/ground_truth`, `/sim/pose`, `/sim/path`, `/sim/markers`, `/sim/scenario`, TF `map→base_link→camera_link` |
| `perception_node` | Model P for potholes, Model B for cracks (D082, never summed), on CUDA; falls back to the simulator's projected boxes when weights or torch are missing, and labels every frame PROJECTION-ONLY | image + ground truth, paired by timestamp | `/perception/detections` (`vision_msgs/Detection2DArray`), `/perception/image_annotated`, `/perception/source` |
| `planner_node` | `build_perception` → `next_state` → `command_for`, **unchanged**; staleness failsafe; logs every episode against the offline simulator | `/perception/detections` | `/cmd_vel` (`geometry_msgs/Twist`), `/planner/drive_state`, `/planner/markers` |

ROS is **one more `Transport`**: `RosTransport` implements
`certain_road.canbus.transport.Transport` and publishes each `Command` as a Twist in
physical units (m/s and rad/s). The decision code cannot tell ROS from CAN (D049, D050).

| Problem | Fix |
|---|---|
| ROS install stopped silently (GitHub API rate limit) | Version read from the releases redirect; errors now printed (§4) |

the dashcam footage does not swerve. A video demo is **open loop**: real road, real Model P
and Model B, real ground truth, and the planner's live decision on every frame. This is what

## 15. For the next Claude Code agent (on the Mac): build "three videos → which road first"

**Read first:** CLAUDE.md; docs/DECISIONS.md D006, D010, D049, D075, D079–D082, D088, D093–D099;
docs/design.md §3; this log; ros/MENTOR-DEMO.md. Work on a branch off `main`, one decision entry
per design choice, `uv run python scripts/check_repo.py` green before every commit. The Mac
runs torch on MPS (`core.device.available_device` keeps that); ROS and Gazebo are Jetson-only.

**Goal.** `uv run python scripts/survey_videos.py road_a.mp4 road_b.mp4 road_c.mp4 [--camera ...]`
surveys each video as one road and writes one offline HTML report that ranks where to repair
first across all three, in the style of `runs/survey_environments/report.html`.

**Reuse, don't rewrite:** detection and confirmation as `scripts/live_video.py` /
`scripts/eval_video.py` (`confirm_step`, D075; P for potholes, B for cracks, D082); scoring through
`certain_road.survey` exactly as `sim/mujoco/survey.py` feeds it (footprints by
`core.geometry` IPM, segments, deducts, vision-estimated PCI); RSL from `survey/rsl.py`; pooled
plans from `survey/allocation.py` as `scripts/survey_environments.py` does; the report from
`dashboard/survey_report.py` with a frame gallery (crop, model, score, segment, **video time** as
the location, GPS only if the video carries it).

**The hard parts, which must be decided and logged, not guessed:**
- *Camera geometry.* Vision-estimated PCI needs ground footprints, which need camera height,
  pitch and HFOV. Real dashcams have none. Take them as `--camera` arguments (or a per-video
  YAML), default to the design camera (configs/project.yaml `sim:`), and say in the report that
  areas, and so PCI, are only as right as those numbers.
- *Distance.* D006 samples every 5 m; a video has no odometer. Use `--speed-kmh` (or GPS) and say
  segment lengths are estimates.
- *No ground truth.* Report detections and vision-estimated PCI, not recall. D080: silence is not
  a good road; run the drift monitor (D078) and flag roads whose footage is out of distribution.
- *Speed of inference.* Process every frame (D088), or sample with a stated, justified stride.
