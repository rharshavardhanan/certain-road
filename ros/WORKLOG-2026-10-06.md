## 3. Torch on the GPU

The repo pins `torch==2.13.0` from PyPI in `uv.lock`. On Linux aarch64 that wheel is
already a CUDA 13 build, so **no change to `pyproject.toml` or `uv.lock` was needed**.

- `uv` 0.12.23 installed to `~/.local/bin` (user space, no sudo).
- The project venv was created on the **system** Python so ROS's `rclpy` can load into it:
  `uv venv --system-site-packages --python /usr/bin/python3 .venv`, then `uv sync`.
- Result: `torch 2.13.0+cu130`, `torchvision 0.28.0+cu130`, `ultralytics 8.4.115`,
  `opencv 5.0.0`, `numpy 2.5.1`. `torch.cuda.is_available()` is True and the device is `Orin`.
- Torch warns that sm_87 (Orin) is not in its build list (sm_80, sm_90, sm_100, sm_110,
  sm_120). The sm_80 kernels run correctly on it. Checked rather than assumed:
  - conv + batchnorm + SiLU, GPU against CPU: max absolute difference 6.6e-7
  - `torchvision.ops.nms`, GPU against CPU: identical output
  - fp16 works; a small conv stack took 4.6 ms at 640x640
- A throwaway probe venv `~/.venvs/certain-road` (torch 2.14.1+cu130) was used for the
  first test. It is not used by anything and can be deleted.

## 4. ROS 2 Jazzy install

Script: `~/install_ros_jazzy.sh` (outside the repo). It follows the official
ros2-apt-source method from docs.ros.org and:

1. adds an **8 GB swapfile** (`/swapfile`, plus a line in `/etc/fstab`), because the Orin
   Nano has 7.3 GB RAM and no swap, and VS Code + RViz + torch use most of it
2. installs the official `ros2-apt-source` package (version 1.3.0)
3. installs `ros-jazzy-desktop`, `ros-dev-tools`, `ros-jazzy-vision-msgs`,
   `ros-jazzy-cv-bridge`, `python3-opencv`
4. adds `source /opt/ros/jazzy/setup.bash` to `~/.bashrc`

**Problem hit and fixed.** The first run stopped silently after `apt update`. The docs read
the ros2-apt-source version from `api.github.com`, and this network's public IP is over
GitHub's unauthenticated API rate limit ("API rate limit exceeded"). The lookup returned
nothing and `set -e` ended the script with no message. The script now reads the version
from the `github.com/.../releases/latest` redirect, which is not the API, downloads with
`curl -f`, checks the file is a real `.deb`, and prints `!! stopped at line N` on any error.

Installed: `ros-jazzy-desktop 0.11.0`, `ros-dev-tools 1.0.3`, `ros-jazzy-vision-msgs 4.1.1`.
Verified with `ros2 run demo_nodes_cpp talker` / `demo_nodes_py listener` ("I heard: Hello
World").

**numpy 2 is fine.** ROS Jazzy's message libraries are built against Ubuntu's numpy 1.26,
and the project venv has numpy 2.5.1. Checked: messages with fixed-size float arrays
(`PoseWithCovariance`), `vision_msgs/Detection2DArray` and a 640x640 `Image` all serialize
and deserialize, and publishing works. No separate environment is needed.

## 5. What was built

The pasted plan said to wrap the existing simulator so the camera view it "already
renders" goes out as `sensor_msgs/Image`. **The 2D simulator renders no camera image:**
`sim/project.py` turns each pothole straight into a box. A renderer was added first.

### The ROS graph

```
sim_node ──/camera/image_raw──▶ perception_node ──/perception/detections──▶ planner_node
   ▲      ──/sim/ground_truth─▶                                                  │
   └──────────────────────────────────── /cmd_vel (Twist) ◀──── RosTransport ◀───┘
```

| Node | Does | In | Out |
|---|---|---|---|
| `sim_node` | Steps the bicycle model (`sim.model.step`) with the latest `/cmd_vel`; renders the camera frame; runs the 8 trial-matrix scenarios in turn | `/cmd_vel` | `/camera/image_raw`, `/sim/ground_truth`, `/sim/pose`, `/sim/path`, `/sim/markers`, `/sim/scenario`, TF `map→base_link→camera_link` |
| `perception_node` | Model P for potholes, Model B for cracks (D082, never summed), on CUDA; falls back to the simulator's projected boxes when weights or torch are missing, and labels every frame PROJECTION-ONLY | image + ground truth, paired by timestamp | `/perception/detections` (`vision_msgs/Detection2DArray`), `/perception/image_annotated`, `/perception/source` |
| `planner_node` | `build_perception` → `next_state` → `command_for`, **unchanged**; staleness failsafe; logs every episode against the offline simulator | `/perception/detections` | `/cmd_vel` (`geometry_msgs/Twist`), `/planner/drive_state`, `/planner/markers` |

ROS is **one more `Transport`**: `RosTransport` implements
`certain_road.canbus.transport.Transport` and publishes each `Command` as a Twist in
physical units (m/s and rad/s). The decision code cannot tell ROS from CAN (D049, D050).

## 7. Problems found and fixed along the way

| Problem | Fix |
|---|---|
| ROS install stopped silently (GitHub API rate limit) | Version read from the releases redirect; errors now printed (§4) |
| Renderer took 84.5 ms per frame, too slow for 10 Hz | Ground rows sliced instead of masked, int16/uint32 arithmetic: 30.6 ms |
| A near pothole's rendered disc was wider than its projected box | Not a renderer bug. `project_pothole` takes the width at the disc's centre distance, which under-reports it close up (1–2 % at the ~0.9 m decision distance, 7 % at 0.5 m). Left unchanged because the CI trial matrix is asserted on it; the test pins the measured agreement |
| RViz camera panel was ~200 px wide, unreadable | Panel sizes generated with PyQt5 (`ros/rviz_window_state.py`) and stored in `demo.rviz` |
| Drive-state text did not show in RViz | The marker was stamped "now", newer than any TF; now stamped zero and frame-locked |
| Episodes cut short by stopping the launch were reported as "differs" | A stopped episode is compared on the frames it reached |
| The first episode of a launch can lose frame 0 (sent before ROS discovery completes) | `sim_node` now waits until the whole loop is connected before starting. Re-run: episode 0 got all 60 frames and matched offline, as did every episode after it |
| `pytest` hangs with ROS sourced | One of the pytest plugins ROS installs auto-loads and stalls. Run tests with `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1` when ROS is sourced |

## 8. What the demo does and does not show

- **PROJECTION-ONLY today.** The detector weights are gitignored and not on the Jetson. Until
  they are copied, the boxes are the simulator's ground truth; the log, `/perception/source`
  and every frame say so.
- **The rendered frames are not photographs.** Flat-shaded asphalt with dark discs is far
  outside the RDD2022 photos the detectors were trained on, so even with the weights the
  models are not expected to fire on them.
- **D050's limits still apply:** no motion blur, vibration, lighting, real command latency or
  actuator dynamics.
- In `blocked_right`, the planner takes AVOID_LEFT although the hazard is slightly left of
  centre, because the right is blocked. This is the existing trial-matrix behaviour, asserted
  in CI, and is unchanged.

## 10. Paused: the real road video

The user asked to show the models on real Indian roads with real ground truth, from video.

**One limit up front:** a recording cannot be steered. When the planner says AVOID_LEFT,
the dashcam footage does not swerve. A video demo is **open loop**: real road, real Model P
and Model B, real ground truth, and the planner's live decision on every frame. This is what
D052 already specifies (recorded video → real YOLO → decision). No simulation is both fully
real and steerable; only the physical robot is.

**What the repo already has:**

- Clip `2DV-cYmIvT4` (RT Dashcam, Indian roads, CC BY), expected at
  `data/video/2DV-cYmIvT4.mp4` (gitignored, on the Mac).
- Ground truth `configs/eval/gt/2DV-cYmIvT4_claude.csv`: 17 potholes counted as time
  intervals over 120–180 s. One annotator (an AI pass), interval-only, no boxes.
- Earlier scores on that window (`results/video/2DV-cYmIvT4/gt_score.json`):

  | Model | Potholes caught | False alarms per minute |
  |---|---|---|
  | P | 10 of 17 | 20 |
  | B | 4 of 17 | 1 |

**Planned design (not started):**

- A `video_node` that plays the clip into the same graph in place of `sim_node`, either in
  real time or lockstep (each frame waits for its detections, so none are skipped).
- `/camera/camera_info` from both sources, so the planner reads the image size instead of
  assuming the robot camera's 640x640.
- `perception_node` stops requiring simulator ground truth in detector mode; the overlay
  shows "GT: pothole in view" from the CSV at the frame's video time.
- `planner_node` logs every decision with its video time, so each GT pothole can be checked
  for a reaction, and each reaction outside a GT interval counted as a false manoeuvre.
- Re-run `scripts/eval_video.py` and `scripts/score_video_gt.py` on the Jetson with CUDA (the
  config says `device: mps`, the Mac's backend).

## 11. How to run

```bash
cd ~/certain-road
source /opt/ros/jazzy/setup.bash && (cd ros && colcon build)   # after any code change
source ros/env.sh                                              # every new terminal
ros2 launch certain_road_ros demo.launch.py                    # all 8 scenarios + RViz
```

In a second terminal (after `source ros/env.sh`): `rqt_graph`, `ros2 topic hz /cmd_vel`.

Per-episode results: `runs/ros/<UTC stamp>/episodes.jsonl`.

Record the screen:

```bash
gst-launch-1.0 -e ximagesrc display-name=:1 use-damage=false ! video/x-raw,framerate=15/1 \
  ! videoconvert ! x264enc speed-preset=ultrafast tune=zerolatency bitrate=6000 \
  ! h264parse ! mp4mux ! filesink location=runs/ros/capture/demo.mp4
# Ctrl+C stops it and finalises the file
```
